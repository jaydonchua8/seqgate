# seqgate

Accept or reject candidates in an automated search without fooling yourself by looking early or by testing many candidates.

This is an independent prototype that I wrote on my own. It is not affiliated with Aemon and nobody there has reviewed it. All data in this repository is synthetic and generated by the code here.

## The problem

A search loop proposes a candidate, evaluates it against the current baseline, and keeps it if it looks better. Three things go wrong quietly when the evaluation is noisy.

1. The loop checks the score after every evaluation and stops the first time a significance test passes. A 5% test used that way is not a 5% test.
2. Most candidates are not improvements, so even a correct 5% test per candidate lets a large share of the accepted candidates be noise.
3. Every accept becomes the new baseline, so a wrong accept is built on by everything that follows and is reported as progress.

In the benchmark below, on a synthetic retrieval task, a one-sided 5% z-test checked after every query accepted 34.0% of candidates whose true effect was exactly zero. In a 60 candidate search, 33.1% of what it accepted was not an improvement.

## What it does

- `Gate` is a sequential test on the sign of each paired difference. It needs no bound on the scores.
- `MeanGate` is a sequential test on the size of each paired difference, for scores with a known bound such as a per-query Recall@10. It tests "the mean difference is at most zero".
- Both keep the chance of accepting a non-improvement under `alpha` no matter how often you check, and both stop early.
- `MeanGate` also runs a mirrored test for harm and stops a clearly worse candidate early with reason `worse`.
- A crashed or timed out candidate run is counted as the worst possible outcome on that unit (`update_failed()`), not skipped.
- `Ledger` hands out the level for each new candidate so that a guarantee holds over the whole search: either the chance of any false accept (`spend`) or the false discovery rate, the expected share of accepts that are not improvements (`elond`).
- `retrieval.py` is a synthetic BM25 retrieval task used as a test bed, and `bench.py` measures everything on it.

```python
from seqgate import MeanGate, CONTINUE
from search import Ledger

ledger = Ledger(alpha=0.05, mode="elond")
for candidate in proposals:
    gate = MeanGate(alpha=ledger.next_alpha(), max_n=1000, bound=1.0)
    for query in stream_of_queries():
        try:
            c = evaluate(candidate, query)
        except Exception:
            decision = gate.update_failed()
        else:
            decision = gate.update(evaluate(baseline, query), c)
        if decision != CONTINUE:
            break
    ledger.record(gate.decision == "accept")
    if gate.decision == "accept":
        baseline = candidate
```

## Architecture

| file | role |
|---|---|
| `seqgate.py` | `Gate`, `MeanGate`, `run()`, the CSV command line tool |
| `search.py` | `Ledger` and the `gamma` weight series |
| `retrieval.py` | synthetic corpus and query generator, BM25 with a weighted title field, Recall@10 |
| `bench.py` | tuning on a dev generator, held-out gate table, search comparison |
| `demo.py` | one search under two acceptance rules, printed accept by accept |
| `test_seqgate.py`, `test_search.py`, `test_retrieval.py` | tests |
| `bench_results.json` | output of the last full `bench.py` run |
| `example_scores.csv` | twelve made-up score pairs for the command line tool |

How a gate works: it keeps a wealth that starts at 1. Before each unit it chooses a bet from past units only. `Gate` multiplies the wealth by `1 + bet` on a win and `1 - bet` on a loss. `MeanGate` multiplies it by `1 + bet * x`, where `x` is the difference divided by the bound. If the candidate is not better, the expected multiplier is at most 1, so the wealth cannot grow on average, and by Ville's inequality the chance that it ever reaches `1 / alpha` is at most `alpha`. That holds at every check, which is why stopping early is allowed.

How the ledger works: candidate `k` is tested at `alpha * gamma_k * (accepts so far + 1)`, where the `gamma_k` sum to at most 1. This is the e-LOND rule from Xu and Ramdas, "Online multiple testing with e-values" (https://arxiv.org/abs/2311.06412), which controls the false discovery rate under arbitrary dependence between candidates. The docstring in `search.py` has the short argument for why.

## Key decisions and tradeoffs

- **Betting tests, not a corrected z-test.** A group sequential design fixes the look schedule in advance. A search loop does not have one, so I wanted a guarantee that holds at any stopping time. The cost is power: at the budget, a single z-test is stronger (see the table).
- **A declared bound, enforced.** `MeanGate` raises on a difference outside the bound and on NaN or infinite scores. Clipping silently would keep the test valid but hide a broken evaluator, and NaN used to be read as a tie.
- **Failures are the worst case.** Skipping failed runs would let a candidate that crashes on hard inputs look better than it is.
- **False discovery rate, not a union bound, as the default.** The union bound gets strict fast in a long search. e-LOND loosens the level after every accept. In this benchmark the two ended up close, because searches had about two accepts.
- **A slow weight series.** `gamma_k` decays like `1 / (k ln^2 k)` so the thousandth candidate can still be tested. The first version used `1 / k^2`.
- **Harm stop is separate from the accept test.** It can only remove accepts, so it cannot raise the false accept rate, and it rejects a truly better candidate with probability at most `harm_alpha`.
- **Tuned on one generator, measured on another.** The two bet settings were picked on a simple parametric generator and then frozen. The gate table and one of the two search tables use a retrieval corpus with a different seed and different generator settings.

## Install and usage

Python 3, standard library only. Nothing to install.

```
python demo.py                       # about 10 seconds of CPU
python -m unittest                   # 47 tests, about a minute of CPU
python bench.py                      # full benchmark, about 2 minutes of CPU
python bench.py 0.1                  # smoke run, does not overwrite bench_results.json
python seqgate.py example_scores.csv                          # sign gate on a CSV of baseline,candidate
python seqgate.py example_scores.csv 0.05 40 --mean --bound=0.05
```

The command line tool exits 0 on accept, 1 on reject and 2 on bad input. A candidate cell of `fail` marks a failed run.

## Tests and verified results

`python -m unittest` runs 47 tests: the 14 from the first version unchanged, 23 for `MeanGate`, the ledger and the command line tool, and 10 for the retrieval task. They include simulated false accept rates at the boundary for three difference shapes, a check that the futility stop never changes a decision, out of bound and non-finite inputs, failed runs, malformed CSV files, and a search where a fixed level breaks the false discovery rate and e-LOND holds it.

The numbers below are from one full run of `python bench.py` (5% level, budget of 1000 queries per candidate) and are stored in `bench_results.json`.

Tuning on the dev generator chose `lam_max=0.9, prior_var=0.25` out of six settings. Those are now the defaults.

One candidate against a fixed baseline, held-out retrieval corpus, 1000 trials per cell and 4000 for the null. The null column uses real per-query differences with a random sign, so the true mean is exactly zero. The other columns group configurations by their true effect.

| method | null: accepted | queries | 0 to 0.01: accepted | queries | 0.01 to 0.03: accepted | queries | above 0.03: accepted | queries |
|---|---|---|---|---|---|---|---|---|
| z-test, peek every query | 34.0% | 723 | 54.8% | 602 | 98.9% | 121 | 100.0% | 47 |
| z-test, fixed budget | 5.2% | 1000 | 26.8% | 1000 | 97.6% | 1000 | 100.0% | 1000 |
| seqgate Gate (sign) | 2.2% | 924 | 10.9% | 928 | 88.9% | 374 | 100.0% | 129 |
| seqgate MeanGate | 1.7% | 977 | 6.1% | 974 | 91.9% | 413 | 100.0% | 158 |

Search: a hill-climb over 140 BM25 configurations from a deliberately untuned start, 60 candidates per search, 100 searches. Every accept becomes the new baseline.

Dev corpus (start 0.6217, best configuration in the grid 0.6733):

|---|---|---|---|---|---|
| z-test, peek every query | 14.8 | 34.5% | 100.0% | 809 | 0.6720 |
| MeanGate, 5% per candidate | 2.4 | 0.0% | 0.0% | 834 | 0.6702 |
| MeanGate + spend (union bound) | 1.7 | 0.0% | 0.0% | 811 | 0.6676 |
| MeanGate + e-LOND ledger | 1.8 | 0.0% | 0.0% | 807 | 0.6681 |

Held-out corpus (start 0.5558, best configuration in the grid 0.6049):

| rule | accepts | share of accepts that were not improvements | searches with any false accept | queries per candidate | final Recall@10 |
|---|---|---|---|---|---|
| z-test, peek every query | 15.7 | 33.1% | 100.0% | 790 | 0.6017 |
| MeanGate, 5% per candidate | 2.9 | 0.2% | 1.0% | 818 | 0.6008 |
| MeanGate + spend (union bound) | 1.9 | 0.0% | 0.0% | 785 | 0.5957 |
| MeanGate + e-LOND ledger | 1.9 | 0.0% | 0.0% | 782 | 0.5959 |

What I take from this:

- The guarantees held. `MeanGate` accepted 1.7% of exact nulls against a 5% limit, and the peeking z-test accepted 34.0%.
- `MeanGate` beat the sign gate where the effect was moderate (91.9% against 88.9%) and lost to it on the smallest effects (6.1% against 10.9%). Most per-query differences in this task are exactly zero, which suits a sign test.
- Early stopping saved real work on large effects (158 queries against 1000) and almost nothing on nulls (977 of 1000).

## Limitations and next steps

- **The gate did not produce a better final system here.** The ungated search reached 0.6017 on the held-out corpus and the e-LOND search reached 0.5959. In this landscape the wrong accepts are tiny steps sideways, and accepting many small true improvements is worth more than refusing them. What the gate buys is that the list of accepted changes can be trusted: about a third of the ungated search's accepts were not improvements, and that list is what would be reported as progress. Whether that trade is right depends on how costly a wrong claim is, and I do not know that for Aemon's customers.
- **Low power on small effects.** At the budget, the fixed z-test accepted 26.8% of the smallest real improvements and `MeanGate` 6.1%. A larger budget or a better bet (for example a mixture over bets) is the next thing I would try.
- **Nulls cost the whole budget.** The futility bound for `MeanGate` is loose and rarely fires. A candidate with a true effect near zero runs for about 977 of 1000 queries.
- **Everything is synthetic.** The corpus is generated from a seed, the candidates are points on a parameter grid and not code changes, and I have not run this on scores from a real experiment system.
- **Fresh queries are assumed.** Each candidate is evaluated on queries drawn independently from a pool. If thousands of candidates reuse one fixed eval set, the search can overfit that set, and nothing here detects it. A held-back split checked rarely would be the first step.
- **The bound has to be known.** `MeanGate` does not work for unbounded scores such as a loss. `Gate` does, at the price of ignoring effect size.
- **The stopped estimate is biased.** `mean_diff` in the summary is the average at the moment of stopping, which overstates the effect for accepted candidates. I do not correct it.
